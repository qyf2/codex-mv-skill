# 审片与交付

## 看图而非只看代码

每镜头的进入/关键姿态/反应/退出，镜头接缝前后各约 0.25 秒，脸、手和持物接触点都要有视觉依据。
从纸面读分镜的观众并不知道后续剧情：一眼能否理解事件，反应是否早于原因，动作有没有不连贯的瞬移？
转场可能遮住剧情或歌词，必须逐帧检查。连续帧用于判断动作，稀疏关键帧不能证明运动流畅。

新工程先用 2–4 帧验证引擎。预览成功后才开始整段渲染；预估时间以同一场景的真实 ms/frame 为准。
并行 worker 共享 GPU/CPU，数量翻倍不代表耗时减半；软件渲染默认从 1 开始。

## 歌词与音轨

试听开头、片段中间、副歌/转场及结尾。检查第一句是否带入上一句、LRC offset 方向是否正确、
选段是否重复减过起点、行间空白是否清屏、中文是否缺字、最后几个字是否被截断。
基本 LRC 的近似高亮不能描述为已经通过逐字演唱对齐。

## 成片技术检查

```text
ffprobe -v error -show_entries format=duration:stream=codec_type,codec_name,width,height,r_frame_rate,nb_frames -of json out/video.mp4
ffmpeg -v error -i out/video.mp4 -f null -
ffmpeg -y -ss 1 -i out/video.mp4 -frames:v 1 out/check/encoded-1s.png
```

打开从 MP4 解码的图片检查，而不只检查编码前的 JPEG。预期 H.264 + yuv420p、带音频时 AAC。
实际帧数应为 `ceil(duration * fps)`；指定 range 时为范围内帧数，端点不包含最后时刻。
AAC 有编码延迟，容器时长可有很小差异；明显超出一帧或缺失尾句应继续调查。
编码器会为较短音频补静音到视频结束，因此技术时长正确也不证明音乐完整，必须试听。
无 ffprobe 时可用 FFmpeg 的流信息/解码检查补充，但如实说明验证工具的限制。

## 交付内容

MP4、工程、`STORYBOARD.md`、源歌词/转换后的时间轴（用户允许分享时）、节拍数据和已审预览图。
不要把 node_modules、数万帧缓存、私有歌曲或凭据提交到公共 GitHub。
报告实际时长、分辨率、帧率、音轨、渲染地点、主要命令和实测速度。
没有实际渲染的作品写“工程已就绪，待本地渲染”；没有视觉审查的内容写“尚未视觉审片”。
